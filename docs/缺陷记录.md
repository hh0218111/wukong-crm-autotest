发现日期：2026-11-17

## BUG-001 线索客户名越界未被业务层校验，数据库异常直接暴露为 HTTP 500

| 项 | 内容 |
|---|---|
| 严重级别 | 中（功能可用但错误处理缺失，且泄露服务端实现细节） |
| 优先级 | P2 |
| 模块 | CRM / 线索管理 / 新建线索 |
| 接口 | `POST /crm/leads/save` |
| 环境 | 本机 phpstudy：Nginx 1.15.11 + PHP 7.3.4 + MySQL 5.7.26 |
| 状态 | 待修复（已提交回归用例守护） |

### 复现步骤
1. 以管理员账号登录，取得 `authKey` 与 `sessionId`
2. 调用 `POST /crm/leads/save`，请求体 `{"name": "<256个字符>", "mobile": "<未占用号码>"}`
3. 观察响应

### 预期结果
返回 HTTP 200 + 业务错误码（如 `code:400`），提示"客户名长度不能超过255个字符"，与系统已有的重名校验（返回 `code:400 该字段值重复`）保持一致的错误处理风格。

### 实际结果
返回 **HTTP 500**，响应体是 ThinkPHP 的 System Error 调试页，直接暴露数据库异常：

```
SQLSTATE[22001]: String data, right truncated:
1406 Data too long for column 'name' at row 1
```

### 根因分析（分层定位）
| 层 | 结论 |
|---|---|
| 页面层 | 前端可能有 maxlength 限制，但接口层可绕过 |
| 接口层 | `crm/leads/save` 未对 `name` 做长度校验，请求直接透传到 Model |
| 数据层 | `5kcrm_crm_leads.name` 定义为 `varchar(255)`；写入256字符触发 MySQL 1406 |
| 框架层 | 生产配置未关闭调试模式，异常堆栈以 HTML 调试页返回给客户端 |

**两个独立问题**：① 业务层缺少长度校验；② 异常处理未收口，数据库错误细节外泄（信息泄露风险）。

### 边界值实测数据（支撑用例设计）
| 输入长度 | 结果 | 判定 |
|---|---|---|
| 26 字符 | `code:200` 创建成功 | 正常，原先误判为"超长"已修正 |
| 255 字符 | `code:200` 创建成功（DB 实测 `CHAR_LENGTH=255`） | 边界内，符合预期 |
| 256 字符 | **HTTP 500 + SQLSTATE 22001** | **缺陷** |

### 修复建议
1. 在 `application/crm/model/Leads.php` 的验证规则中补 `name` 长度约束：`'name' => 'require|max:255'`
2. 长度上限不要写死，与字段定义保持单一来源（读表结构或统一常量）
3. 生产环境关闭 `app_debug`，异常统一转为业务错误码，避免堆栈外泄
4. 同类字段（客户、商机、合同名称）应一并排查是否存在相同缺口

### 回归守护
`tests/api/test_leads_api.py::test_create_leads[256字符越界应被校验拦截而非抛异常]`
该用例当前**故意保持失败**，修复后应自动转绿。断言不只是"创建失败"，而是要求 `HTTP 200`——确保修复方式是业务校验，而不是继续抛异常。

## 附：实测摸清的接口契约（非缺陷，供后续用例复用）

| 项 | 实测结论 |
|---|---|
| 入口 | `http://localhost/72crm/index.php`（ThinkPHP pathinfo 路由） |
| 登录 | `POST /admin/base/login`，body `{username, password}` |
| 鉴权 | 自定义头 `authKey` + `sessionId`；用 `Authorization` 会返回 `code:101 请先登录` |
| 成败判定 | HTTP 恒为 200，业务码在响应体：`200` 成功 / `400` 校验失败 / `101`、`302` 未登录 |
| 线索字段 | 客户名字段是 `name`（**不是** `customer_name`） |
| 唯一性校验 | `name` 与 `mobile` **均有唯一性校验**，重复提交返回 `code:400 该字段值重复` |
| 列表查询 | `POST /crm/leads/index`，body `{page, limit, search}` |
| 删除 | `POST /crm/leads/delete`，body `{id: [...]}`（参数名是 **id** 不是 ids，写错会静默不删） |

> 唯一性校验这条直接决定了用例设计：固定测试数据会让用例第二次执行必然失败，
> 因此框架用 `RUN_ID` 后缀 + 动态手机号保证幂等，并在用例结束后清理数据。
